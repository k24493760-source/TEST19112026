## Фактическое поведение токенизатора MiniLM

Измерено, не из карточки:

- `max_seq_length` runtime = **256** (карточка: 256; архитектура BERT допускает 512, ST режет до 256).
- Текст на 1840 токенов обрезается до 256; вектор длинного текста **не равен** вектору короткого префикса-предложения.
- Предупреждение Hugging Face: последовательность длиннее 256 «will result in indexing errors» — ST всё равно truncate=True при `encode`.
- Практический запас без обрезки: порядка **~200 токенов MiniLM** на синтетическом русском тексте (в прогоне `tokens_fit=206`, `chars_fit=303`).
- Чанки шага 2.3Б с лимитом ~600 токенов **будут обрезаны** при текущем эмбеддере.

## Совместимость с УКЗ-15 (проект, не внедрялось)

1. **Размерность хранения.** MiniLM: 384 — совпадает с `Vector(384)`. E5-base: 768. BGE-M3 и E5-large: 1024. Смена модели **кроме MiniLM / e5-small** требует смены типа колонки.
2. **Повторный чанкинг.** Существующие draft-чанки под токенизатор MiniLM с size≈600 **нельзя** честно эмбеддить MiniLM без обрезки. Для E5 (512) и BGE (8192) лимит токенов другой: переиспользовать текст чанка можно, но нужен пересчёт `token_count` токенизатором новой модели. Для юридического контура безопаснее перечанкить под выбранный лимит.
3. **Инкремент.** Эмбеддить только чанки новой `document_version` / нового `chunkset`. Публикация атомарно переключает `corpus_version`.
4. **Запрет смешивания.** Один live-индекс — одна `(embedding_model, embedding_dim, model_revision)`. Иначе cosine бессмыслен.
5. **Фиксация версии.** Поля на `published_release` / `chunkset`: `embedding_model`, `embedding_dim`, `embedding_revision` (hash весов), `corpus_version`. На чанке: `chunk_id`, `document_version`, `corpus_version`, `embedding_model`.
6. **Схема без ломки live.** Не менять `Vector(384)` in-place. Вариант: таблица `chunk_embeddings(chunk_id, model_key, dim, vector)` + отдельный индекс; либо колонка `embedding_1024` только после отдельной миграции на копии БД. Старые векторы MiniLM оставить до пересчёта и cutover.

`apply_embeddings` сейчас не пишет `embedding_model`. Смена модели без колонки версии смешает пространства.

## Выводы

1. **Лучшее измеренное качество** — только MiniLM: остальные кандидаты **не запускались**. Сравнивать качество нельзя.
2. **Оптимум для MVP на этой машине** — оставить `all-MiniLM-L6-v2` + `Vector(384)`. Это единственная локально воспроизводимая модель. Для русскоязычной нормы она уже даёт промахи на отрицаниях и близких терминах; гибридный TF-IDF в `retrieve_chunks` частично компенсирует это в проде, но в этом шаге dense считался отдельно.
3. **Фактически выполнено:** инвентаризация кода; зонд токенизатора MiniLM; 34 gold-запроса; Recall@5 / MRR@10 / nDCG@10; latency embed/search; RSS; skip остальных по RAM/кэшу; карточки лицензий и префиксов E5/BGE (без прогона).
4. **Не проверены:** BGE-M3, E5-base, E5-large (нет весов, ~0.2 ГБ RAM, нет GPU). Метрики для них **не имитировались**.
5. **Чтобы внедрить не-384 модель:** новая колонка/таблица векторов, правка `EMBEDDING_DIM` и проверки в `embedder.py`, префиксы E5 в `embed_texts` (passage) и `embed_text` запроса (query), не смешивать индексы, полный пересчёт live-векторов, согласование лимита чанка с `max_seq_length`.
6. **Шаг 2.4Б.** Можно переходить **только как проектирование/каркас** поверх MiniLM (версия модели в релизе, запрет смешения, лимит чанка ≤256 токенов MiniLM). **Нельзя** на 2.4Б менять продуктивную модель на E5/BGE: нет сравнительных метрик и нет ресурсов для честного прогона. Повтор сравнения — на машине с ≥16 ГБ RAM (лучше GPU) и локальным кэшем весов, без выгрузки корпуса заказчика во внешние API.
